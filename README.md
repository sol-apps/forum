# 💬 Forum

A 2004-style internal message board where signed-in staff post to fixed categories
under a pseudonym, with threads, flat replies and author-only deletion.

Generated by the [Greenlight](https://greenlight.solhann.net) build wizard, and
delivered as a pull request rather than a deploy — a human approving that pull
request is what lets this app exist.

- **Spec:** [`spec.json`](spec.json) — the capabilities, scopes and tier this app
  declares, agreed with the builder before any code was written.
- **Conventions:** [`AGENT.md`](AGENT.md) — node-free static frontend, PocketBase
  hooks, vendored design system.
- **CI:** every pull request is checked against `spec.json`. Code that contradicts
  its own spec does not merge.

## How it is put together

- `index.html` — the board index: three categories, topic and post counts, last post.
- `category.html?c=<slug>` — topics in a category, ten to a page, plus the new topic form.
- `thread.html?t=<id>` — a topic and its replies, with a delete button on your own posts.
- `pb-auth.js` — the identity seam. Email and password against PocketBase's `users`
  collection, token in `localStorage`, sent as `Authorization` on every call.
- `pb_hooks/` — the only way in to the data. The `categories`, `threads` and `posts`
  collections are superuser-only at the API-rule level, so the browser cannot read
  them directly and the `author` relation never reaches a reader.

## Pseudonymous, not anonymous

Every post stores the account that wrote it, in a relation no read path returns.
Readers see a handle. An administrator with database access sees the account. The
UI says this in three places, because the failure mode of a board like this is
someone believing the handle protects them.

## Running it locally

```bash
pocketbase serve --publicDir . --hooksDir ./pb_hooks --dir ./.pb_data --migrationsDir ./pb_migrations
```

Then open http://127.0.0.1:8090.
